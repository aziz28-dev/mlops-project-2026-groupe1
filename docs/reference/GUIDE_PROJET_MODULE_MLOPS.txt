  Ambition Industrielle : Votre Carte de Visite d’Excellence pour le PFE et l’Emploi

  Le passage d’un algorithme de Machine Learning fonctionnant isolément dans un notebook Jupyter
  à un système autonome, robuste et monitoré en production constitue aujourd’hui le défi
  numéro 1 des équipes Data mondiales.
  L’objectif fondamental de ce projet intégrateur (Capstone Project) est de construire une véritable
  plateforme MLOps de niveau entreprise, couvrant 100% de la chaîne de valeur de l’IA in-
  dustrielle. Vous ne livrerez pas un simple modèle : vous déploieriez une infrastructure logicielle
  vivante, testée en intégration continue, conteneurisée, orchestrée et capable de détecter
  ses propres dérives pour s’auto-réentraîner. Ce projet constitue la pièce maîtresse de votre
  portfolio d’ingénieur et un tremplin direct vers votre Projet de Fin d’Études (PFE).



  Compétences Opérationnelles Évaluées à l’Issue du Projet

      1. Software Engineering : Modularisation stricte (src/), typage statique, docstrings et linters
         (flake8, black).
      2. Data Versioning : Gestion des données et pipelines reproductibles via DVC et stockage
         distant.
      3. Expérimentation & Gouvernance : Suivi des runs, métriques, artefacts et promotion de
         modèles avec MLflow Registry.
      4. Inference Serving & Packaging : Création de microservices REST FastAPI et conte-
         neurisation Docker non-root.
      5. CI/CD & CML : Automatisation des tests (Pytest) et génération de rapports de métriques
         sur Pull Request (GitHub Actions + CML).
      6. Orchestration & CD : Exécution résiliente de flux DAG et déploiements zero-downtime
         (Blue/Green, Canary) avec Prefect 3.x.
      7. Observabilité & Feedback Loop : Détection de Data Drift (KS, χ2 , PSI), métriques
         Prometheus et réentraînement autonome.

  Démarche Directrice & Philosophie MLOps du Projet

  Un projet de Machine Learning en entreprise ne se résume jamais au score prédictif d’un modèle.
  La réussite d’un ingénieur MLOps repose sur trois règles d’or incontournables :
     — 1. Reproductibilité Absolue : N’importe quel membre de l’équipe ou un nouvel arrivant
         doit pouvoir réexécuter l’intégralité du pipeline en 3 commandes de terminal (git clone,
         dvc pull, pytest) et obtenir exactement les mêmes résultats.
     — 2. Défense en Profondeur & Tests Systématiques : Aucun code ne peut être fusionné
         sur la branche main sans que les tests unitaires, les tests de validation de schéma et les
         vérifications de linting ne soient au vert dans GitHub Actions.
     — 3. Résilience & Boucle de Rétroaction : Tout modèle déployé est appelé à dériver sous
         l’effet du temps et de l’évolution des comportements. Votre plateforme doit être capable de
         mesurer sa propre santé statistique et de réagir avant même que l’utilisateur final ne
         perçoive une dégradation.



  Conseils d’Organisation pour le Mode Projet Agile

      — Travaillez en branches Git dédiées : Ne committez jamais directement sur main. Créez
        des branches par fonctionnalité (feature/dvc-pipeline, feature/fastapi-serving, etc.)
        et utilisez les Pull Requests pour déclencher les workflows CI et CML.
      — Commencez simple, itérez vite (MVP MLOps) : Mettez en place un modèle de base
        (baseline rapide) et validez la chaîne complète (Git → DVC → FastAPI → Docker → CI)
        dès les premières semaines avant d’optimiser les hyperparamètres.
      — Documentez au fil de l’eau : Remplissez votre README.md et vos docstrings dès l’écriture
        du code pour gagner un temps précieux lors de la rédaction du rapport final.

1.1. Déclinaison des 7 Piliers Techniques Obligatoires
   — Pilier 1 (Craftsmanship) : Code propre organisé sous src/, séparation des responsabilités,
      régles PEP8, pyproject.toml.
   — Pilier 2 (DVC) : Suivi des datasets volumineux sans surcharger Git, configuration d’un remote
      (local ou cloud) et définition des étapes dans dvc.yaml.
   — Pilier 3 (MLflow) : Logging de plusieurs architectures (ex : XGBoost vs RandomForest vs
      LogReg), traçabilité des matrices de confusion, et promotion formelle vers le statut Production.
   — Pilier 4 (Serving) : Endpoints /predict et /health typés avec Pydantic, gérant l’inférence
      unitaire et batch. Image Docker légère (ex : python:3.11-slim) exécutée sous utilisateur non-
      root.
   — Pilier 5 (CI/CD & CML) : Workflow GitHub Actions déclenchant le linting (flake8, black)
      et la suite de tests pytest. Publication automatique d’un rapport de métriques et graphes en
      commentaire de Pull Request.
   — Pilier 6 (Prefect) : Flow principal décoré @flow enchaînant les tâches atomiques @task avec
      gestion des retries, déploiement déclaratif prefect.yaml, Work Pool et déclenchement planifié.
   — Pilier 7 (Drift & Réentraînement) : Mesure statistique rigoureuse des écarts de distribution
      (test KS pour le numérique, χ2 pour le catégoriel, et calcul formel du PSI). Export au format
      OpenMetrics pour Prometheus et déclenchement autonome du réentraînement si le drift est critique
      (≥ 30%).

3. Critères de Sélection du Dataset & Directives Méthodologiques
   Le choix d’un dataset adapté conditionne directement la faisabilité de la chaîne MLOps :
3.1. Critères d’Éligibilité Obligatoires d’un Dataset
   — Volume de données : Entre 2 000 et 200 000 lignes (Taille idéale : 5 000 à 50 000 enregistre-
      ments, fichier < 100 Mo). Évitez les datasets gigantiques (> 500 Mo) qui dépassent les quotas de
      temps d’exécution de GitHub Actions gratuit.
   — Typologie mixte : Le jeu de données doit comporter au moins 5 variables numériques et au
      moins 2 variables catégorielles afin de pouvoir illustrer les différents tests de dérive (KS pour
      le continu, χ2 pour le catégoriel).
   — Cible métier explicite : Problème de classification (binaire ou multiclasse) ou de régression
      clairement défini répondant à une vraie décision d’entreprise.
   — Potentiel de Data Drift réaliste : Présence d’une dimension temporelle ou possibilité de dé-
      finir une sous-population / décalage réaliste pour simuler l’avant (baseline) et l’après (flux de
      production).
   — Licence libre : Données sous licence ouverte (CC, MIT, Open Data, Kaggle, UCI).
3.2. Portails de Données Recommandés
   — Kaggle Datasets : https://www.kaggle.com/datasets (Recherchez par thématique : Banking,
      Health, Retail, Energy).
   — UCI Machine Learning Repository : https://archive.ics.uci.edu/ (Référence acadé-
      mique et industrielle).
   — OpenML : https://www.openml.org/ (Nombreux jeux de données déjà nettoyés avec bench-
      marks).
   — Portails Publics Nationaux : https://www.data.gouv.fr/, Eurostat, World Bank Open Data.

  Datasets Strictement Interdits (Jeux de Données Scolaires Jouets)

  Pour garantir un niveau ingénieur professionnel, les jeux de données académiques élémentaires sui-
  vants sont formellement interdits : Titanic, Iris de Fisher, Boston Housing, California Housing,
  MNIST, Wine Quality, Palmer Penguins.
